== 2. Expected cost per correct answer = cost per attempt / accuracy ==
accuracies below are ILLUSTRATIVE except the three marked "mea" (measured in ch3_react.py: 12 questions x 3 repeats; the plain ReAct
loop, not the guard + improved tool version). A cost per correct answer with zero correct answers is undefined.
pattern                                     accuracy  $ / attempt  $ / correct
direct answer                                  3% mea       0.0050       0.1782
chain of thought                              22% mea       0.0098       0.0439
ReAct, 5 tool steps                           56% mea       0.0607       0.1093
plan-and-execute, 5 steps (parallel)          80% ass       0.0364       0.0456
tree of thoughts, b=3, d=3                    90% ass       0.2552       0.2835
best-of-5 with a model verifier               80% ass       0.0780       0.0975
best-of-5 with a free checker (tests)         90% ass       0.0488       0.0542

reading: a pattern that costs 10x more per attempt is still cheaper per correct answer only if it is also more than 10x as accurate,
or if a wrong answer has a cost of its own (a human review, a refund, a retry) that you add to the numerator.

== 3. With a verifier (tests, a checker, a human), retry up to k times ==
P(success within k) = 1 - (1 - p)^k      expected cost = c * (1 - (1 - p)^k) / p      (c = cost of one attempt, p = pass rate per attempt)
ASSUMES: attempts independent; the same p and the same cost c on every attempt; a PERFECT verifier (accepts every right answer,
rejects every wrong one). Feedback-driven retries break the first two (attempt 2 sees attempt 1), and real verifiers are not perfect.
one attempt c = $0.0098 (chain of thought, frontier price)

reading: with a verifier, retries raise the success rate quickly (p=0.5, k=3 gives 88%) and the cost per correct answer barely moves,
because failed attempts are cheap and recognised. Without a verifier there is nothing to retry on: you pay k times and keep the same accuracy.

== 4. ReAct input tokens against step count ==
ASSUMES: the loop replays the FULL growing history on every call (quadratic); plan-and-execute executors see a bounded context
(linear). Two common changes: prompt caching bills the repeated prefix at a discount (CACHE_RATE below, an assumption: providers
differ), and compaction keeps only the last WINDOW steps in full. Columns: billed-equivalent input tokens.
CACHE_RATE = 0.1 (cached tokens cost 10% of normal input), WINDOW = 3 steps
 steps  ReAct full  + caching  + compaction  plan-exec  ratio full/plan
     2       5,850      2,745         5,850      5,210             1.1x
     5      15,750      4,950        14,400      8,150             1.9x
    10      41,250      9,525        28,650     13,050             3.2x
    20     126,000     22,050        57,150     22,850             5.5x
reading: the quadratic growth is a property of full replay, not of ReAct itself; caching changes the bill (not the context size or
the attention cost), and compaction changes both at the price of forgetting detail.

== 5. P(correct | accepted) = p*r / (p*r + (1-p)*f) ==
p = P(candidate correct), r = P(accept | correct), f = P(accept | wrong). The false-accept rate f is NOT 1 - precision.
    p     r     f  P(correct | accepted)

worked example: p=0.9, r=1, f=0.2 gives 0.9 / (0.9 + 0.02) = 97.8%. At p=0.3 the same verifier gives 68.2%: an acceptance
means less on hard tasks, where most candidates are wrong.
